# F1: Data Reality

Question: **can these numbers be trusted?**

F1 is the only phase allowed to look inside the data. Every later phase inherits
what you decide here, so a wrong grain or an unnoticed duplicate makes the whole
run worthless while still looking finished.

Nothing in F2 to F7 is legal until F1 closes.

## Before the first cell

`profile.json` was produced without a model. It already holds file names, sizes,
sha256, row counts, column names, and inferred dtypes. Read it with `read_file`.
Do not spend cells recomputing what is already printed there.

What the profile cannot tell you, and what F1 must establish: what one row means,
which rows are duplicates, what is missing and why, and which metrics this data can
actually support.

## Step order

Run these in order. One cell per step unless the step says otherwise. Do not clean
before the audit is complete: a cast applied in step 2 changes the duplicate count
you measure in step 4.

| # | Step | Must print |
|---|---|---|
| 1 | inventory: per file, rows, columns, dtype, hash | `file=… rows=… cols=… sha256=…` |
| 2 | grain: candidate keys, uniqueness ratio, exact duplicates | `key=… unique=… rows=… ratio=…` |
| 3 | partial duplicates: same key, different payload | count, plus 3 example rows |
| 4 | missingness map | per column: `missing=… pct=…` |
| 5 | type audit: numeric as text, dates as text, decimal comma, currency, leading zeros | offending column, example value, proposed cast |
| 6 | joins: candidate keys between files, cardinality, fan-out risk | `pair=… left_unique=… right_unique=… cardinality=…` |
| 7 | metric eligibility: which metrics are computable | `metric=… verdict=… reason=…` |
| 8 | cleaning: apply the casts and drops you decided | rows, cols, nulls before and after |

Step 8 is the only step that writes `derived/`. Keep the source files untouched.

## Grain

A row is not automatically a transaction, and a column named `id` is not
automatically a key. State the grain in one sentence, for example: "one row is one
invoice line, and one invoice can have several lines".

- Test every candidate key for uniqueness. Print the ratio, not a yes or no.
- Exact duplicates: count and percentage. Record them; do not drop them yet.
- Partial duplicates: the key is unique but the payload disagrees. Print which
  column conflicts. A key that is unique on 99 percent of rows is not unique.
- If no candidate key is unique, the grain is unknown. Say so, aggregate at no
  level, and put the consequence in `cannot_answer`.

Grain test, printed as a ratio:

```python
print("rows=%d cols=%d" % df.shape)
for keys in [["invoice_id"], ["invoice_id", "sku"]]:
    n = df.drop_duplicates(keys).shape[0]
    print("key=%s unique=%d ratio=%.4f" % ("+".join(keys), n, n / len(df)))
```

## Missingness

- Report per column: count and percentage.
- Classify the pattern. Random missing is tolerable; systematic missing is a
  finding. Test it by grouping the missing flag by month, segment, or file, and
  print the split.
- Missing because of the value itself is the third pattern and the dangerous one:
  customers who churned stop answering, expensive items hide their price, failed
  orders lose their amount. Do not impute it away. If a metric depends on that
  column, print a best-case and worst-case bound and record the bias as a
  limitation.
- Missing in a metric column is not the same as missing in a dimension column.
  A row with no price cannot be summed away, it can only be excluded.
- Above 40 percent missing: exclude the column from analysis and mark it `dibuang`
  in the dictionary. Keep it in the file, do not delete it silently.

## Type traps

Check each of these explicitly. They are common in small-business exports and each
one corrupts a total if missed.

| Trap | Symptom | Consequence |
|---|---|---|
| Decimal comma | `1.234,56` or `1,5` | sum returns zero or a string error |
| Currency prefix | `Rp 1.200.000`, `1,2jt` | column is object dtype |
| Mixed date formats | `03/04/2025` and `2025-04-03` | wrong month, wrong trend |
| Numeric-looking id | `00123` | leading zeros lost on cast to int |
| Negative quantity or price | `-2`, `-150000` | return, correction, or error, decide which |
| Two names for one entity | `Total`, `TOTAL`, `total ` | segments split in two |
| Whitespace and case | ` Jakarta`, `JAKARTA` | same city counted twice |

For each, print the before and after: the distinct count, or the parsed min and max
date. A cast you cannot verify is a cast you should not apply.

## Joins

Only relevant with more than one input file.

- Pick the key that is unique on the dimension side. If both sides are unique,
  prefer the one with fewer nulls.
- Print row counts before and after the join. If the count grows, the join fanned
  out, and every revenue total after that point is inflated.
- Fan-out has two legal fixes: deduplicate the dimension, or aggregate the fact
  table to the dimension grain first. Never accept fan-out and continue.
- Record the join in `cleaning_log.json` with `rows_before` and `rows_after`.

## Groups

`profile.json` lists `datasets`: groups of files that share a key. Files in
different groups have no join path between them, so a join across groups
produces empty rows or a fan-out, never a real table.

- Join only inside one group.
- Analyse every group that appears in `profile.json`, the small ones included. A
  group of one file is still a dataset, not a leftover to ignore. When the run
  has more than one group, each group runs as its own unit and `profile.json`
  lists only that unit's group.
- Never invent a key to attach a group to another group. If two files must be
  compared but share no key, say so in `cannot_answer` instead.
- State the grain per group; two groups can have different grains.

## Metric eligibility

Fill this table completely. It is the contract for every later phase.

| Metric | Computable when | Otherwise |
|---|---|---|
| revenue | a nominal column exists and sign rules are known | state it, no estimate |
| orders | a unique order identifier, or grain is one row per order | do not report a count |
| average order value | revenue and orders both computable | state which side is missing |
| units sold | a quantity column, returns identified | state it |
| gross margin | a cost column exists | `cannot_answer`, never estimate a cost |
| customer retention | a customer identifier exists | F4 will skip itself |
| change over time | a parseable date column | no trend, no growth, F2 loses its spine |
| discount impact | a discount column below 40 percent missing | state the coverage |

A row that says "cannot" removes that metric from the entire run. It does not
reappear later as a hypothesis, a scenario, or a sentence in the report.

## Required outputs

1. `evidence/F1.json`: findings for grain, duplicate rate, missing rate on every
   used column, join cardinality, and each metric verdict.
2. `notes/data_dictionary.md`: one row per column of the cleaned data, including
   dropped columns marked `dibuang` with the reason.
3. `notes/cleaning_log.json`: one entry per operation, each with `reason` and
   `reversible`.
4. `cannot_answer`: every metric excluded in step 7, phrased as a question the data
   cannot answer.

Every finding needs a printed number behind it. "Data terlihat bersih" is not a
finding and cannot carry an `E-###`.

## When the data is not ready

If there is no date column and no nominal column, or if no column can be trusted
enough to aggregate at all, stop the run here.

Write the report version "data belum siap": what the file contains, what is
missing, and what the owner needs to add to make the analysis possible. Then call
`finish("blocked", ...)`.

This is a valid outcome, not a failure. A run that reports unready data honestly is
worth more than a run that produces confident numbers from a broken file.

## Prohibited in F1

- Charts. F1 produces numbers, not pictures.
- Business conclusions ("penjualan bagus"). That is F2.
- Causal language. That is F3.
- Dropping rows before the duplicate count is recorded.
- Inferring a column's meaning from its name. If `total` might be before or after
  discount, say which you assume, and record it in `warnings` and the dictionary.
- Renaming columns for taste. Keep the original names; rename only when two
  columns collide after a merge.

## Exit check

All of these must be true before `advance_phase`:

- grain stated in one sentence, with the uniqueness number behind it
- every column either used or dropped, with a reason in the dictionary
- all eight metrics in the eligibility table answered
- `evidence/F1.json`, `data_dictionary.md`, and `cleaning_log.json` written
- `cannot_answer` reviewed; if empty, the reason it is empty is stated
- row count of the cleaned data reconciled with the source, difference explained
