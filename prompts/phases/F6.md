# F6: Penantang

Question: **which findings do not survive a second look?**

F6 attacks. It does not complete, extend, or improve the analysis, and it does not
produce a better version of a finding. It takes every `E-###` the run intends to
report and tries to break it.

Success in F6 is measured by demotions, not confirmations. A run where every finding
survives is possible, but it should be the result of work, not of a short checklist.

The attack is also a claim, so it needs a number. A finding is never demoted because
it "feels weak": it is demoted because a cell printed the counter-value, or because
the artifact does not contain the value at all.

## Entry condition

F2, F3, and F5 are closed, and F4 has finished or marked itself inapplicable.

Build the ledger from the files, not from memory:

1. `read_file` every `evidence/F{n}.json`.
2. List every `E-###`, one row per id.
3. Read `cells/index.json` for the cell and status behind each id.

An id you did not list is an id you did not audit, and the controller requires all of
them.

## The ledger

One row per finding, filled as the audit proceeds:

| Field | Values |
|---|---|
| id | `E-###` |
| printed | `yes`, `no` |
| status_ok | `yes`, `no` |
| base_same | `yes`, `no`, `n/a` |
| population_same | `yes`, `no`, `n/a` |
| subgroups_checked | `yes`, `no`, `n/a` |
| decision | `keep`, `demote`, `remit` |

`remit` means the defect is fixable inside its own phase. That is not a demotion: it
is a return, and it uses the transition table.

## Attack order

Cheapest first. Stop attacking an id when one attack succeeds; record the rest as not
reached rather than pretending they passed.

| # | Attack | Kills the finding when |
|---|---|---|
| 1 | printed | the value is not in the artifact of the cell that claims it |
| 2 | status | the producing cell is not `status=ok` |
| 3 | base | the comparison period or the baseline changed between statement and number |
| 4 | denominator | a ratio is quoted without both sides, or the population behind it moved |
| 5 | subgroup reversal | the sign flips inside two or three large segments |
| 6 | small n | a rate rests on fewer than 30 observations, or a trend on fewer than six periods |
| 7 | period comparability | partial period, unequal days, a gap, or a mid-window change in how data was collected |
| 8 | grain leakage | the number was computed on a frame that fanned out on a join |
| 9 | definition drift | a column changed meaning inside the window (price before or after discount, merged category) |
| 10 | arithmetic | the number was derived by hand from two printed values and never printed itself |
| 11 | ratio versus point | a share moving from 40 to 35 is `-5 poin persentase`, not `-12,5%` |
| 12 | conditionality | an F5 branch value quoted without its "jika" |

## Attack 1: is it printed

Open the artifact named in the entry. Search for the `display` string, or the value it
renders.

```
artifact=cells/019.out.txt  needle=-12,4%  found=yes
```

- `found=no` means the finding is an interpretation, not a measurement. Demote.
- If the artifact is missing or the cell errored after printing, the entry is not
  evidence regardless of how plausible the number looks.
- Re-executing the cell is allowed and sometimes necessary. Re-execute only
  computations that do not depend on mutated state, and compare the new output to the
  artifact. A value that changes on re-run is a reproducibility failure: record it in
  `verification.rerun` and demote every finding that rests on it.
- If re-execution cannot be done without disturbing the kernel state, say
  `rerun=skipped` and record why. Do not claim a re-run you did not perform.

## Attack 2 to 4: base, denominator, population

A change with the wrong base is not a change. Check three things against the
statement:

- the period named in the statement matches the period in the computation
- the baseline named is the baseline used, not a neighbouring one
- the population filtered out the same rows in both periods

For a ratio, print numerator and denominator for both periods before deciding. A
conversion rate that fell while its numerator rose is a denominator finding, and the
sentence in the report must say which side moved. If only the ratio was recorded,
recompute both sides now and mint an `E-###` for the pair.

## Attack 5: subgroup reversal

This is the Simpson test applied per finding, not per phase.

1. Take the two or three largest segments of the dimension the finding rests on.
2. Compute the same change inside each segment.
3. Compare signs with the aggregate.

If a large segment moves the other way, the aggregate direction is a mix artifact.
Demote the aggregate claim, keep the segment rates as the reportable finding, and
print the standardised rate so the reversal is quantified rather than asserted.

## Attack 6: small n

| Claim | Threshold | Action |
|---|---|---|
| a rate | fewer than 30 observations behind it | demote `confidence` to `medium`, and demote the finding if the claim depends on it |
| a trend | fewer than six periods | demote: it is a level comparison |
| a cohort | fewer than 30 customers | demote the retention number |
| a funnel step | fewer than 30 orders | cannot be ranked as the worst step |

Print `n` next to the number in the audit cell. "Cukup banyak" is not an audit.

## Attack 7: period comparability

Check every period used for a cited change:

- days covered, printed per period
- a partial final period compared against a full one
- a month with a holiday or a short month, if the metric is volume rather than rate
- a data gap: months with zero rows that were silently skipped
- a channel, store, or product added or removed mid-window

Any of these that was not handled in F2 demotes the change it supports. The fix, when
possible, is a return to F2 with the period handled, not a sentence of apology in the
report.

## Attack 8 to 9: grain and definition

- Re-print the row count before and after every join the finding passed through. A
  frame that grew on a join inflated every sum computed after it.
- Check the definition of every column used, against `data_dictionary.md`. A price
  column that switched from before-discount to after-discount mid-window produces a
  change that is an artefact of bookkeeping, and that is not a business finding.

## Demotion

Demotion is a state change, not a deletion.

1. Set `verified: false` on the `E-###`. The entry stays for audit.
2. Add an `H-###` with the reason and the discriminating number:

   ```
   {"id": "H-004", "statement": "penurunan terpusat pada kanal marketplace; gugur karena tiga segmen terbesar naik dan penurunan hanya terjadi di segmen 4 persen", "status": "rejected"}
   ```

3. List the report section the finding would have fed, so F7 cannot build on it.
4. Keep the counter-number as its own `E-###`, because the demotion is a finding about
   the data and the report appendix must be able to cite it.

A demoted finding is not repaired inside F6. If the defect is fixable in the phase
that produced it, use `remit`: `advance_phase("F3", "audit F6: residual tidak nol pada
dekomposisi E-011")`. The controller allows F6 to return to F2, F3, or F5. Returning
with a reason is cheaper and more honest than patching the number in place.

## When the defect is in F1

There is no return path from F6 to F1. F1 is the foundation: the grain, the metric
verdicts, and the cleaning decisions are inherited by every phase, so a defect there
cannot be fixed by re-measuring one number.

| F1 defect | Response |
|---|---|
| one column's meaning is wrong | demote every finding that used it, record an `AN-###` with `handled: false`, finish `partial` |
| the grain is wrong or unknown | demote every aggregate, finish `partial` with the reason in the report body |
| the metric was never computable | finish `failed`; the report becomes the "analisis terhenti" version |

Do not quietly continue with a known F1 defect. A partial report that names its
foundation problem is worth more than a complete report built on it.

## Contradictions between phases

Two findings about the same quantity with different values are a defect in the run,
not a nuance.

- The later measurement wins only if it is genuinely more specific: narrower
  population, better base, or a corrected definition. The statement must say what
  changed, and the earlier id is demoted with that reason.
- If neither is more specific, demote both. Keeping the friendlier one is choosing a
  number, not auditing it.
- Record the pair in `notes/f6_audit.md` so the appendix can show both.

## Stopping rule

Stop when every id in the ledger has a decision. Attacks after that point are scope
creep: they cost cells, and the report does not get longer or truer.

## What F6 must not do

- Add analysis beyond the audit: no new segments, no new metrics, no new causal
  hypotheses.
- Demote for style, tone, or "this could be stronger".
- Repair a finding in place and keep the same id when the definition changed.
- Reopen F1. Escalate instead.
- Soften a demotion into "perlu data tambahan" while leaving `verified: true`.
- Keep a finding alive because the report would otherwise be thin. A short report
  made of findings that survived is the product. A long one made of survivors and
  near-misses is the failure mode this phase exists to prevent.

## Files

The ledger is a document for humans, so it goes to `notes/`, not into the evidence
schema:

```
notes/f6_audit.md        one table row per E-###, with the decision and the reason
```

`evidence/F6.json` keeps the shape defined in `CONTRACTS.md` §4, unchanged:

```json
{
  "phase": "F6",
  "question": "temuan mana yang tidak tahan uji",
  "findings": [
    {
      "id": "E-021",
      "pillar": "fact",
      "statement": "tiga segmen terbesar naik 4,1 persen saat agregat turun 12,4 persen pada Q3 2025",
      "value": 0.041,
      "unit": "ratio",
      "display": "+4,1%",
      "cell": 44,
      "artifact": "cells/044.out.txt",
      "dataset_hash": "sha256:...",
      "confidence": "high",
      "verified": true
    }
  ],
  "hypotheses": [
    {
      "id": "H-004",
      "statement": "penurunan terpusat pada kanal marketplace; gugur karena E-021 menunjukkan tiga segmen terbesar naik, dan penurunan hanya terjadi di segmen 4 persen",
      "status": "rejected"
    }
  ],
  "anomalies": [],
  "cannot_answer": []
}
```

Do not invent new top-level keys. If a field is genuinely needed, update
`CONTRACTS.md` first; a schema that drifts per phase cannot be validated.

The section each demoted finding would have fed belongs in its `H-###` statement or
in the ledger, not in a new key.

## No chart

F6 draws zero charts. The audit produces numbers and decisions, and a chart of a
demotion would be a picture of a table the appendix already prints.

## Exit check

All of these must be true before `advance_phase("F7", ...)`:

- ledger covers every `E-###` from every phase, with no blank decision
- every `demote` has either a printed counter-value or an artifact check behind it
- every demoted id has `verified: false` in its own phase file, plus an `H-###` with
  `status: rejected` and the reason
- every `remit` was actually returned to its phase, and that phase re-closed
- F1 defects escalated with an `AN-###`, and the finish status set accordingly
- contradictions resolved by specificity, or both sides demoted
- `notes/f6_audit.md` written
- `evidence/F6.json` written with the contract shape unchanged
- the audit summary printed: `audited=… kept=… demoted=… remitted=…`
- the report can be built from `verified: true` entries only, and every remaining
  entry has a cell that printed its value
